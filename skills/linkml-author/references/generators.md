# Generator pitfalls, by version

Each row names the LinkML version the behaviour was seen on. Re-check a row before relying on it on a newer version, and drop it when upstream fixes it. The project's own version is in `uv.lock`.

| Seen on | Generator | Behaviour | What to do |
| --- | --- | --- | --- |
| 1.11.1 | `gen-json-schema` | A class with `union_of:` becomes an empty `{}` definition with `additionalProperties: false`, so every instance of the union fails | On each slot whose range is the union class, add `any_of:` listing each alternative range; the JSON Schema then carries a proper `anyOf` |
| 1.11.1 | `gen-json-schema` | `additionalProperties: false` is set on every definition, so deeply nested polymorphic data may fail even with the `any_of` workaround | Keep the discriminated alternatives as separate concrete classes; validate samples of each |
| 1.11.1 | `gen-owl` | A rule using `none_of: [{equals_string: X}]` on an enum-ranged slot crashes with `AssertionError: Object None must be an rdflib term` | Write `none_of: [{equals_string_in: [X]}]`, which is equivalent and goes through the `owl:oneOf` path |
| 1.11.1 | `gen-python`, `linkml-run-examples` | A slot whose name is a Python keyword (LOKF's `from`) is written as a field name, so the dataclass module does not compile; enum values are escaped, slot names are not. The example runner compiles the same dataclasses to instantiate each valid example, so `just test` fails on any file under `tests/data/valid/` | Do not import the dataclasses of a schema that has one. The Pydantic module compiles. Validate data with `linkml.validator`, and keep valid examples under `tests/data/problem/valid/`, which the runner skips. linkml 1.12.0 escapes the field as `from_` (PR 3317), but its loaders still reject `from` (PR 4083 is open) |
| 1.11.1 | `linkml.validator.validate(instance, path)` | The schema is loaded without its `source_file`, so a relative `imports:` entry resolves from the working directory | Load the schema with `SchemaView(path).schema` and pass that; or run from the schema's directory. Fixed by linkml PR 3855, released in 1.12.0 |
| 1.11.1 | `linkml-lint` | `standard_naming` walks the import closure, so an imported schema's names are linted with the project's | A `.linkmllint.yaml` in the project directory with `standard_naming.exclude` listing those names |
| 1.11.1 | `gen-doc` | Imported elements get no page unless `--render-imports` is passed, so `is_a: Imported` links to nothing | `LINKML_GENERATORS_DOC_ARGS="--render-imports"` in `config.public.mk` |
| 1.12.1 | `SchemaView`, `linkml-lint`, `gen-pydantic`, `gen-json-schema`, `gen-shacl`, `gen-owl` | Two imports that define one name merge without an error or a warning; of two imports in one list, the one listed last wins | Prefix class names and keep fundamental fields as attributes ([schema-design.md](schema-design.md)); a CI check that walks the closure for duplicate names |
| 1.12.1 | `gen-python`, `gen-jsonld-context`, so `gen-project` | The same duplicate stops them with `Conflicting URIs (<schema>, <schema>) for item: <name>`, so the gate fails where lint passed | Read it as a name defined in two imported schemas, and rename or drop one |
| 1.12.1 | `imports:` by URL or CURIE | `.yaml` is appended to the expanded import, and the module's own relative imports are fetched from the module's address, so a modular root imports over HTTP when every module is served at the same relative path. `SchemaView(url)` appends nothing | Serve every module and a merged file ([publishing.md](publishing.md)); pin the toolkit, since older releases resolved those imports elsewhere |
| 1.12.1 | `--importmap` | A key is a CURIE, an IRI or a `prefix:` namespace; a value omits `.yaml`; a relative value resolves against the directory of the schema the tool was given, nested imports included; the format is undocumented (linkml issue 3844) | `gen-project` takes `importmap` in each generator's `generator_args` in `generators.yaml`, read from the working directory; a single generator takes `--importmap` |
| 1.12.1 | `gen-owl` | Same-named attributes on classes in different modules under one `default_prefix` induce one IRI and a warning `Ambiguous attribute` for each (linkml issue 2403) | One slot with a `slot_uri` when the meaning is one, else a distinct `slot_uri` per attribute |
| 1.12.1 | `gen-owl` | A top-level slot gets an `rdfs:range`; the same field as an attribute does not. The IRI, the JSON-LD context and the JSON Schema are identical either way | Nothing; it is why folding a single-class slot into an attribute is safe |
| 1.11.1 | `gen-project` | Runs neither `gen-pydantic` nor `gen-java`, which the justfile runs separately (linkml issue 2537) | Nothing; the `gen-project` recipe already does |
| 1.11.1 | `linkml-run-examples` | Warns "No counter examples found" once per input format that has no files, even when the other format has them | Nothing; the warning is noise |
| 1.3+ | any | `reachable_from` (dynamic enums) is not resolved at validation time | Materialise first with `vskit expand -s schema.yaml -o schema_expanded.yaml` |
| 1.10 | any | `instantiates:` is not enforced by `linkml-validate` | Treat it as documentation |
| 1.8+ | `gen-pydantic` | Arrays (`array:` on a slot) are supported by the Pydantic generator; other generators lag | Check the generator before relying on array shapes |
